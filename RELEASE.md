# Release Guide

This repository ships `Streamer Pro.exe` as the main GitHub Release asset.
`ffmpeg.exe` and `ffprobe.exe` are required for the app to stream correctly, but they are not bundled in GitHub Releases because those binaries are large and GitHub asset/repository limits make that flow harder to maintain.
When they are missing, the app offers to download them automatically and places them next to `Streamer Pro.exe`.

## Current Release Model

- Version lives in `Streamer/Streamer.csproj`
- Release notes come from `CHANGELOG.md`
- Tag pushes like `v2.2.5` create a draft release through `.github/workflows/create-release.yml`
- `.github/workflows/verify-ffmpeg.yml` builds the app and verifies local FFmpeg checksums when binaries are present
- The published app asset should be the self-contained single-file executable generated by `dotnet publish`
- Users should place `Streamer Pro.exe` inside its own dedicated folder so downloaded FFmpeg binaries can live beside it

## GitHub Setup

Recommended:

1. In the repo, open `Settings` -> `Actions` -> `General`
2. Set `Workflow permissions` to `Read and write permissions`

Fallback:

1. Create a repository secret named `RELEASE_TOKEN`
2. Use a PAT with access to `marcosstgo/Streamer`
3. Required permissions:
   - `Contents: Read and write`
   - `Metadata: Read-only`

`create-release.yml` prefers `RELEASE_TOKEN` when present and falls back to `github.token`.

## Release Checklist

1. Update `Streamer/Streamer.csproj` version numbers
2. Add the new section at the top of `CHANGELOG.md`
3. Build and publish locally:

```powershell
dotnet build "Streamer/Streamer.csproj" -c Release
dotnet publish "Streamer/Streamer.csproj" /p:PublishProfile="Properties\PublishProfiles\Release-win-x64.pubxml"
```

4. Confirm the executable exists:

```powershell
dir "Streamer\bin\Release\publish-selfcontained\Streamer Pro.exe"
```

5. Commit the release changes
6. Push `master`
7. Create and push the version tag:

```powershell
git tag "vX.Y.Z"
git push origin "vX.Y.Z"
```

8. Wait for these workflows to finish successfully:
   - `Create Release Draft`
   - `Verify FFmpeg Checksums`
9. Upload the published executable to the release draft:

```powershell
gh release upload vX.Y.Z "Streamer\bin\Release\publish-selfcontained\Streamer Pro.exe#Streamer.Pro.exe" --clobber -R marcosstgo/Streamer
```

10. Publish the release:

```powershell
gh release edit vX.Y.Z --draft=false -R marcosstgo/Streamer
```

## End-User Installation Model

1. Download `Streamer Pro.exe` from GitHub Releases
2. Put it in a dedicated folder such as `C:\streamerpro`
3. Run it from that folder
4. If `ffmpeg.exe` and `ffprobe.exe` are missing, the app will offer to download them automatically into that same folder

This folder-based setup is recommended because FFmpeg is required for the product, but distributed separately from the main app executable. The distributed `Streamer Pro.exe` should be self-contained so the user does not need to install .NET manually.

## Auto-Update Verification

Before announcing a release, verify the in-app updater end to end:

1. Run an older installed version
2. Confirm it detects the latest GitHub release
3. Confirm the update window downloads the new `Streamer.Pro.exe`
4. Confirm the app closes, replaces the executable, relaunches, and shows the new version

This was validated successfully for the `v2.2.5` release.

## FFmpeg Verification Script

Local check:

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File "tools/verify-ffmpeg.ps1"
```

CI-compatible check for repos without committed binaries:

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File "tools/verify-ffmpeg.ps1" -AllowMissing
```

When `-AllowMissing` is used, missing binaries are treated as expected for the runtime-download model.

## Known Follow-Up

The release draft is automated, but the executable upload is still manual. A future improvement would be extending GitHub Actions to publish `Streamer.Pro.exe` automatically from the self-contained publish profile.
